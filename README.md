# 🤖 Invoice Bot — Корпоративный Telegram-бот для подачи заявок на оплату счетов

**Безопасный шлюз** между сотрудниками и финансовой системой. Собирает заявки на оплату, сохраняет счета в Google Drive, записывает данные в Google Таблицу, создаёт задачи в Битрикс24 — и всё это с централизованным управлением доступом через корпоративный портал.

## Бизнес-цель

Разработать корпоративного Telegram-бота для **децентрализованного сбора заявок на оплату**. Бот выступает в роли защищённого шлюза между сотрудником и финансовой системой (реестр платежей), обеспечивая:

- **Аудит** — каждая заявка привязана к конкретному сотруднику через Bitrix24 ID
- **Контроль доступа** — пользоваться ботом могут только активные сотрудники, проверенные через корпоративный портал
- **Сохранность вложений** — счета хранятся в защищённой папке Google Drive с ограниченным доступом

### Почему Telegram + Google Sheets?

- **Быстрая разработка** — не нужен фронтенд, админка, база данных. Telegram даёт UI, Google Sheets — хранилище
- **Стандарт де-факто** для малого и среднего бизнеса: сотрудники уже в Telegram, бухгалтерия уже в Google Таблицах
- **Не требует обслуживания** — не нужно обновлять, деплоить фронтенд, чинить базу

## Как это работает

### Диалог с ботом (конечный автомат FSM)

Сотрудник нажимает кнопку **«Оставить новую заявку»** (или отправляет `/start`). Бот запускает конечный автомат (FSM) и последовательно запрашивает данные:

| Шаг | Поле | Валидация |
|-----|------|-----------|
| 1/6 | Плановая дата оплаты | `ДД.ММ.ГГГГ`, ≥ сегодня |
| 2/6 | Наименование контрагента | Обязательное, ≤ 200 символов |
| 3/6 | Сумма и код валюты | `15000 RUB`, 20 валют ISO 4217 |
| 4/6 | Статья расхода | Динамический список из Google Таблицы |
| 5/6 | Комментарий | Опционально, кнопка «Пропустить» |
| 6/6 | Статус оплаты | Кнопки: «Новый» / «Оплачено» |
| — | Файл счёта | PDF/изображение, кнопка «Пропустить» |

После заполнения — **HTML-превью** с кнопками «Изменить» у каждого поля. Сотрудник может скорректировать любые данные перед подтверждением.

### Что происходит при подтверждении

1. **Google Таблица** — данные записываются в строку (11 столбцов A–K). ID счета — автоинкремент
2. **Google Drive** — файл сохраняется как `Счет_№N.pdf` в защищённую папку
3. **Битрикс24** — создаётся задача на ответственного сотрудника (должность из настроек)
4. **Telegram-уведомление** — если дата оплаты = сегодня, ответственному в личку
5. **Групповой чат** — каждая заявка дублируется в общий чат компании

## Безопасность и идентификация

### Централизованное управление доступом через Битрикс24

**Никаких отдельных списков, паролей, ручных настроек.** Доступ управляется через единый корпоративный портал.

```
Администратор Битрикс24
  │
  ├─ Заполнил сотруднику поле UF_TelegramID → доступ открыт
  ├─ Деактивировал сотрудника → доступ мгновенно закрыт
  └─ Уволил → доступ заблокирован на следующем сообщении
```

**Как это работает:**
1. Администратор заполняет у сотрудника скрытое поле **UF_TelegramID**
2. Поле скрыто от пользователя — заполняет только администратор
3. При **каждом** сообщении бот делает запрос в Битрикс24: `user.get?FILTER={ACTIVE:true}`
4. Если сотрудник есть в списке активных с matching Telegram ID → доступ разрешён
5. Если нет → `ApplicationHandlerStop` + «Доступ закрыт. Обратись к руководителю отдела»

### Защита от подмены личности

| Механизм | Как работает |
|----------|-------------|
| **Telegram user_id** | Неизменяемый идентификатор, проверяется серверами Telegram. Подделать невозможно |
| **Имя из Битрикс24** | ФИО всегда подтягивается из корпоративного портала, а не из Telegram |
| **ID сотрудника (столбец K)** | `bitrix_id` пишется в каждую строку таблицы — всегда известно, кто создал заявку |
| **Связка Telegram ID ↔ Bitrix24 ID** | Нерушима на уровне API. Один пользователь не может выдать себя за другого |

### Защита данных

- **Google-доступ** — через **сервисный аккаунт** (не OAuth пользователя, не личный аккаунт). У робота нет прав на всё — только на конкретную папку
- **Google Drive** — файлы доступны только сервисному аккаунту. Права ограничиваются после загрузки
- **.env + credentials.json** — `chmod 600`, исключены из git
- **HTTPS** — все API-запросы через TLS (Telegram, Google, Bitrix24)
- **ApplicationHandlerStop** — гарантированная блокировка при отказе в доступе

## Стек технологий и обоснование

| Компонент | Технология | Почему |
|-----------|-----------|--------|
| **Язык** | Python 3.12+ | Лучшая экосистема: TG-боты, Google API, Bitrix24 |
| **Telegram Bot** | `python-telegram-bot` v22 | Async-native, ConversationHandler — золотой стандарт для FSM-диалогов |
| **Асинхронность** | `asyncio` | Неблокирующая работа при параллельных запросах и ожидании Google API |
| **Валидация** | Pydantic v2 | Строгая типизация, кастомные валидаторы на каждое поле |
| **Google Sheets** | `google-api-python-client` | Официальный SDK, сервисный аккаунт |
| **Google Drive** | `google-api-python-client` | Тот же SDK, permissions API |
| **Bitrix24** | `httpx` + REST API | Webhook-авторизация, `user.get`, `tasks.task.add` |
| **Конфигурация** | `pydantic-settings` | `.env` → валидированные типы на старте |
| **Логирование** | `logging` + Loki | Структурированные JSON-логи → Grafana |
| **Деплой** | systemd / Docker | Auto-restart, ротация логов, лимиты памяти |
| **Зависимости** | `uv` | Быстрее pip в 10x |

### Почему async (PTB v22)?

Для неблокирующей работы бота при параллельных запросах от разных пользователей и ожидании ответов от Google API и Bitrix24. Синхронный бот блокировал бы обработку других сообщений на время ожидания API.

### Как исключена подмена пользователя?

`update.effective_user.id` берётся из защищённого TLS-соединения с серверами Telegram. В отличие от `username`, `user_id` **нельзя подменить** в запросе. Это Primary Key для идентификации. Дополнительно: связка Telegram ID → Bitrix24 ID хранится на стороне корпоративного портала.

## Установка и настройка

### Быстрый старт

```bash
git clone https://github.com/Ivan-Baidyk/tg-invoice-bot.git
cd tg-invoice-bot
python3 setup.py   # 11 шагов интерактивной настройки
uv sync            # установка зависимостей
uv run python bot.py
```

### Systemd (production)

```bash
cat > /etc/systemd/system/invoice-bot.service << 'EOF'
[Unit]
Description=Invoice Bot
After=network.target
[Service]
Type=simple
WorkingDirectory=/root/tg-invoice-bot
ExecStart=/root/tg-invoice-bot/.venv/bin/python3 -u bot.py
Restart=always
RestartSec=5
[Install]
WantedBy=multi-user.target
EOF
systemctl daemon-reload && systemctl enable --now invoice-bot
```

## Структура Google Таблицы

### Лист «Заявки» (11 столбцов A–K)

| A | B | C | D | E | F | G | H | I | J | K |
|---|---|---|---|---|---|---|---|---|---|---|
| ID | Дата | План | Сотрудник | Контрагент | Сумма | Статья | Статус | Коммент | Ссылка | ID сотр. |

### Лист «Справочник» (статьи расхода)

Бот читает столбец A **при каждом запросе** — без кэширования. Добавили статью → сразу доступна всем.

## Экономика проекта

### Затраты на разработку

Проект разработан в стиле **vibe-coding** через **Hermes Agent** с использованием модели **DeepSeek V4 Pro**. На токены потрачено ориентировочно **¥15 (~180 руб)**. Весь код написан агентом под управлением инженера — без привлечения дополнительных разработчиков.

### Инфраструктура

**Никаких платных продуктов.** Всё работает на открытом ПО:

| Компонент | Решение | Стоимость |
|-----------|---------|-----------|
| Сервер | VPS за рубежом (Aruba/AWS/Hetzner) | ~500–900 ₽/мес |
| База данных | Google Sheets (бесплатно) | 0 ₽ |
| Файловое хранилище | Google Drive (бесплатно 15 GB) | 0 ₽ |
| Корпоративный портал | Битрикс24 (бесплатный тариф) | 0 ₽ |
| Мониторинг | Grafana Loki (Open Source) | 0 ₽ |
| Telegram Bot API | Бесплатно | 0 ₽ |

**Итого: ~500–900 ₽/мес** за полностью автономную систему.
При масштабировании на более мощный сервер — стоимость единицы мощности снижается. Условно: на сервере за 1500 ₽ можно запустить 3–5 продуктов → **до 500 ₽/мес** на этого бота.
